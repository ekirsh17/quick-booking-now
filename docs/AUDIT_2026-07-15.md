## Part A — Executive summary (launch decision)

**Security / product posture for multi-merchant go-live: High risk — block launch** until Critical/High go-live blockers below are closed or hard-disabled in production.

This was a **net-new E2E sweep** driven by trust boundaries and user journeys, not a re-check of prior SEC-001…004 alone. Prior reports were reconciled only after new findings existed.

### Go-live scope used for severity

| In scope (launch) | Out of launch scope (parked) |
|---|---|
| Multi-merchant / multi-location | Google Calendar (`GOOGLE_CALENDAR_ENABLED`) |
| Stripe billing | PayPal (`PAYPAL_BILLING_ENABLED`) |
| Outbound SMS notify + STOP/START replies | Merchant SMS-intake create openings (`parse-sms-opening`) |
| Email intake → auto-create openings | |
| QR + booking/claim links | |

### Top launch blockers (plain language)

1. **Anyone can enumerate and mutate open slots** via PostgREST (broken slots RLS) — booking integrity / multi-tenant privacy failure.
2. **Unauthenticated ops endpoints** can send SMS / expose Twilio campaign data / dump config if still deployed.
3. **Waitlist enrollment without phone ownership proof** + open `notify_requests` INSERT policy — harassment / non-consensual SMS risk.
4. **Notify SMS links are unsigned** and fall back to `localhost` if `FRONTEND_URL` unset — broken or forgeable claim path.
5. **QR generation and claim-slot merchant SMS base URL** lack proper auth / trusted-origin binding.
6. **Inbound email auth defaults to `warn`** (allows bad auth through) unless production is confirmed `enforce`.
7. **Dual Stripe webhook implementations** without idempotency — billing double-apply risk if both receive events.
8. **Notify timezone uses profile TZ, signup uses location TZ** — multi-location false negatives / missed SMS.

## Part C — Detailed handoffs (implementer-ready)

### SEC-101 — Unauthenticated `sms-canary` SMS send
**Severity:** Critical | **Confidence:** Confirmed | **Gate:** Blocker (if deployed)

**Attack path:**
1. Attacker `POST /functions/v1/sms-canary` with `{ "to": "+1…" }` (`verify_jwt = false`).
2. Function calls `send-sms` with `SUPABASE_SERVICE_ROLE_KEY`.
3. Arbitrary Twilio SMS → cost abuse / spam.

**Evidence:** [`supabase/functions/sms-canary/index.ts`](../supabase/functions/sms-canary/index.ts), [`supabase/config.toml`](../supabase/config.toml) `[functions.sms-canary] verify_jwt = false`.

**Fix direction:** Undeploy / delete from production; or require service-role + allowlisted destinations only. Never accept public `to`.

**Regression risk:** Low. **Verify:** Unauth POST → 401/403; function absent from deployed list.

### SEC-102 — Slots SELECT allows platform-wide open-slot scrape
**Severity:** Critical | **Confidence:** Confirmed | **Gate:** Blocker

**Attack path:** Anon key `GET /rest/v1/slots?status=eq.open` returns all merchants’ bookable slots (PII-adjacent scheduling inventory).

**Evidence:** [`supabase/migrations/20260106120000_fix_slots_rls_anonymous_booking_final.sql`](../supabase/migrations/20260106120000_fix_slots_rls_anonymous_booking_final.sql) — `OR status IN ('open','notified','held')` with no merchant scope. No later migration tightens SELECT.

**Fix direction:** Remove broad public SELECT. Public read only by known `id` via RPC/edge (`claim-slot` / `resolve-slot` with service role), or require signed link params.

**Regression risk:** Medium — [`ClaimBooking.tsx`](../src/pages/ClaimBooking.tsx) direct fetch must move to scoped RPC/edge. **Verify:** Anon list query returns empty/denied; known-id claim still works.

### SEC-103 — Slots public UPDATE without column ownership locks
**Severity:** Critical | **Confidence:** Confirmed | **Gate:** Blocker

**Attack path:** Anon/authenticated PostgREST UPDATE on any `open`/`notified`/`held` row → set `booked`/`open`, potentially other columns; bypass `claim-slot` SMS and race controls. Also enables client hold-release abuse (BUG-105).

**Evidence:** [`supabase/migrations/20260113234349_fix_slots_rls_public_booking.sql`](../supabase/migrations/20260113234349_fix_slots_rls_public_booking.sql) policy `slots_update_public_booking` — USING/WITH CHECK only constrain `status`.

**Fix direction:** Drop public UPDATE. Booking transitions only via `claim-slot` (service role + atomic CAS). Optional trigger freezing `merchant_id` / times.

**Regression risk:** Medium — remove ClaimBooking client status UPDATEs. **Verify:** Direct anon UPDATE fails; claim-slot succeeds.

### SEC-104 — `notify_requests` INSERT `WITH CHECK (true)` still live
**Severity:** Critical | **Confidence:** Confirmed | **Gate:** Blocker

**Attack path:** Direct PostgREST INSERT into `notify_requests` for arbitrary `merchant_id` / `consumer_id` → later `notify-consumers` SMS.

**Evidence:** Created in [`20251029084230_…sql`](../supabase/migrations/20251029084230_3b3b7c0b-5e72-407d-adaf-e453240124f9.sql). Guest SELECT/UPDATE/DELETE dropped in [`20260603130000_guest_notify_request_rpcs.sql`](../supabase/migrations/20260603130000_guest_notify_request_rpcs.sql) — **INSERT policy never dropped** (repo-wide: no `DROP POLICY` for `"Anyone can create notify request"`).

**Fix direction:** Drop policy. Inserts only via hardened `upsert_guest_notify_request` (+ tight authenticated-owner policy if needed). Update [`ConsumerNotify.tsx`](../src/pages/ConsumerNotify.tsx) paths that still `.from("notify_requests").insert(...)`.

**Regression risk:** Medium — authenticated insert paths must use RPC. **Verify:** Anon direct INSERT fails; guest RPC still works after SEC-105.

### SEC-105 — Guest waitlist RPCs without phone ownership proof
**Severity:** High | **Confidence:** Confirmed | **Gate:** Blocker

**Attack path:** Call `create_guest_consumer_profile` / `get_consumer_auth_status` / `upsert_guest_notify_request` with victim phone → enroll or mutate waitlist; when slot opens, victim receives SMS (and attacker may have enrolled them).

**Evidence:** Guest RPCs in SEC-002 / guest notify migrations; product `authStrategy: "none"` for notify in [`src/utils/authStrategy.ts`](../src/utils/authStrategy.ts); [`ConsumerNotify.tsx`](../src/pages/ConsumerNotify.tsx).

**Fix direction:** Require OTP (or signed short-lived proof) before guest mutate; stop returning existing consumer IDs without proof; rate-limit RPCs.

**Regression risk:** Medium–High (waitlist UX friction). **Verify:** Third-party phone enroll fails without OTP end-to-end.

### SEC-108 / SEC-109 — Unsigned claim links + UI fallthrough
**Severity:** High | **Confidence:** Confirmed | **Gate:** Blocker

**Attack / user path:** `notify-consumers` builds `${FRONTEND_URL||http://localhost:8080}/claim/${slot.id}` with signing “temporarily disabled”. ClaimBooking intentionally falls through to unsigned fetch when `sig` absent. Combined with SEC-102, scraped UUIDs are enough to claim.

**Evidence:** [`notify-consumers/index.ts`](../supabase/functions/notify-consumers/index.ts) ~374–388; [`ClaimBooking.tsx`](../src/pages/ClaimBooking.tsx) ~146–147, 206–255; signing helpers in `shared/slotSigning.ts` / `resolve-slot`.

**Fix direction:** Require `FRONTEND_URL`; re-enable HMAC booking URLs; require valid signature in UI (sunset unsigned links).

**Regression risk:** Medium (old SMS links). **Verify:** SMS URL contains `sig`; unsigned `/claim/:id` rejected or limited.

### SEC-110 — `generate-merchant-qr` unauthenticated
**Severity:** High | **Confidence:** Confirmed | **Gate:** Blocker

**Evidence:** [`generate-merchant-qr/index.ts`](../supabase/functions/generate-merchant-qr/index.ts); `verify_jwt = false`.

### SEC-111 — `claim-slot` Origin-based merchant approve URL
**Severity:** High | **Confidence:** Confirmed | **Gate:** Blocker

**Attack path:** Attacker POSTs claim with `Origin: https://evil.example` → merchant SMS contains phishing approve link (`resolveAppBaseUrl` prefers Origin).

**Evidence:** [`claim-slot/index.ts`](../supabase/functions/claim-slot/index.ts) `resolveAppBaseUrl` L20–46. Contrast: `confirm-booking` prefers trusted env and rejects localhost.

**Fix direction:** Use only `FRONTEND_URL` / `APP_BASE_URL` allowlist (match confirm-booking).

**Regression risk:** Low (local needs env). **Verify:** Spoofed Origin ignored; SMS uses configured base URL.

### SEC-113 — Inbound email auth default `warn`
**Severity:** High | **Confidence:** Confirmed | **Gate:** Blocker until CFG-102

**Attack path:** If `INBOUND_WEBHOOK_AUTH_MODE` unset → `warn` → invalid/missing auth still allowed → forged provider payloads can create openings + trigger notify (token secrecy becomes sole gate).

**Evidence:** [`shared/inboundWebhookAuth.ts`](../supabase/functions/shared/inboundWebhookAuth.ts) `resolveMode` defaults to `warn`.

**Fix direction:** Production must be `enforce` + basic/shared secret configured. Optionally pin sender domains.

**Regression risk:** Medium (provider cutover). **Verify:** Bad auth → 401 when enforce.

### SEC-114 — Dual Stripe webhooks without idempotency
**Severity:** High | **Confidence:** Confirmed | **Gate:** Blocker if both receive events

**Attack / ops path:** Express `/webhooks/stripe` and Edge `stripe-webhook` both verify signatures and upsert subscriptions. `billing_events.provider_event_id` has no unique claim-before-process. Double delivery → double state apply / duplicate usage rows. Edge may return 200 even on handler failure (no Stripe retry).

**Evidence:** [`server/src/routes/stripe-webhook.ts`](../server/src/routes/stripe-webhook.ts), [`supabase/functions/stripe-webhook/index.ts`](../supabase/functions/stripe-webhook/index.ts).

**Fix direction:** Single production endpoint; unique `(provider, provider_event_id)` + claim-before-process; non-2xx on failure.

**Regression risk:** Medium. **Verify:** Replay same event id → no double apply (CFG-104).
